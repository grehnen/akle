# Daily trips come from a pre-generated, committed schedule

Åkle is a static, client-only app, so unlike Travle there is no server to pick each day's start/destination pair. Instead of deriving the pair in the browser from a date-seeded PRNG, a seeded script generates an append-only schedule from the neighbor graph. Each entry is keyed by trip number and records the start, the destination and the shortest-route length N. The schedule is committed, reviewed and bundled with the app. We chose this so the trips can be reviewed and curated, and so a change to the neighbor graph can't silently rewrite past or upcoming trips. The build fails if the graph gives a different N for any entry from today onward. Each entry is checked against the graph version for its trip number ([ADR 0004](./0004-versioned-graphs-keyed-by-trip-number.md)).

The schedule is stored in chunks of 1,000 trips (`data/schedule/0001.csv`, `0002.csv`, …), and each generation run appends one chunk. It is append-only per row, not per file: a trip that has been played never changes, while unplayed rows may still be reconciled against a new graph version (redrawn when they break any schedule rule, see [ADR 0004](./0004-versioned-graphs-keyed-by-trip-number.md)) or curated by hand. A pair repeats only once every pair with the same N has been used (least-used first), so the schedule never runs out of pairs. The one exception: when every less-used pair with that N has an endpoint in a cooldown, a more-used pair may come first, so the cooldowns can't stall generation.

## Consequences

- Anyone reading the bundle can see future trips. We accept this, as Kommunle and early Wordle did.
- The schedule has to be extended before it runs out. Launch generates 10 chunks (trips 1–10,000, about 27 years), so the deployed site keeps serving trips even if nobody touches the repo and every automation breaks: GitHub disables scheduled workflows after 60 days without activity in a public repo, and pinned actions, the Cloudflare tooling and tokens can all rot. A quarterly job is a backstop: it opens an extension PR when fewer than 730 days remain and turns on auto-merge when fewer than 365 remain. CI fails when fewer than 100 remain. (The job originally ran monthly, opened the PR under 90 days and auto-merged under 40, and CI failed under 40; that relied on the automation working every few months, so the thresholds were raised when launch moved to 10 chunks.)
- The app fetches only the chunk holding today's trip, so the download doesn't grow as the schedule does.
- The epoch, trip #1, is fixed once a trip is played: the schedule rules check fails when it differs from the base revision's. Before launch it moved freely; the launch PR moved it from the fixture epoch, 2026-10-01, to 2026-10-26 and replaced the fixture trips, which nobody outside development had played.
